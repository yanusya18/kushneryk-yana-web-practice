# Підготовка до захисту ПР 8

## Контрольні питання

**1. Що таке REST? Які HTTP-методи ідемпотентні?**
REST — стиль API, у якому **ресурси** (місця, бронювання) мають адреси (`/api/items/1`), а дії над ними виражаються
**HTTP-методами**: GET — прочитати, POST — створити, PUT — замінити, DELETE — видалити. Сервер не зберігає стан клієнта
між запитами (stateless), а відповідь містить статус-код і дані (у нас JSON).
**Ідемпотентні** методи — ті, де повторення того самого запиту дає той самий стан сервера: **GET, PUT, DELETE** (а також HEAD, OPTIONS).
Приклад: повторний `PUT /api/items/7` з тими самими даними нічого не змінює; повторний `DELETE` вже нічого не видаляє (відповідь 404, але стан той самий).
**POST не ідемпотентний**: двічі `POST /api/items` створить два місця (у нас вдруге — 409 через унікальну назву, але загалом POST створює новий ресурс щоразу).

**2. Поясніть коди стану 200, 201, 204, 400, 404, 500.**
- **200 OK** — успіх, є тіло (GET, PUT).
- **201 Created** — створено новий ресурс (POST місця, бронювання); у нас ще й заголовок `Location`.
- **204 No Content** — успіх, тіла немає (DELETE).
- **400 Bad Request** — клієнт надіслав некоректні дані (валідація, зламаний JSON); у відповіді перелік `errors`.
- **404 Not Found** — ресурсу або маршруту немає.
- **500 Internal Server Error** — помилка на сервері (баг, збій диска); клієнту — загальний текст, подробиці лише в лозі.
- Також у проєкті **409 Conflict** — запит коректний, але суперечить стану: час уже зайнятий, назва вже існує, місце має майбутні бронювання.

**3. Що таке CORS і чому браузер блокує запити без нього?**
Браузер за політикою **same-origin** не дозволяє сторінці з одного «походження» (схема + хост + порт), напр. `http://localhost:5173`, читати відповіді
іншого (`http://localhost:3001`). **CORS** — механізм, за яким сервер заголовком `Access-Control-Allow-Origin` явно дозволяє певні джерела.
Без нього сервер запит отримає й виконає, але браузер не віддасть відповідь JavaScript-коду. У проєкті дозволені джерела
задаються в `CORS_ORIGIN` (`server/.env`), а middleware `cors({ origin })` додає заголовок. Це захист користувача в браузері, а не захист сервера (curl CORS ігнорує).

**4. Як працює middleware в Express?**
Middleware — функція `(req, res, next)`, яка виконується між отриманням запиту й відповіддю. Express викликає їх **по черзі в порядку підключення**
(`app.use`). Кожна може прочитати/змінити `req`/`res`, завершити відповідь або викликати `next()`, щоб передати керування далі.
Обробник помилок має чотири аргументи `(err, req, res, next)` і викликається, коли десь кинули помилку.
У проєкті: `requestLogger` → `cors` → `express.json` (розбирає тіло) → маршрути → `notFound` (404) → `errorHandler` (500).

## Пояснення ключових фрагментів
- **`server/src/app.js`** — складає застосунок; порядок middleware важливий (404 і обробник помилок — в кінці).
- **`config.js`** — `dotenv` читає `.env`; решта коду користується `config`, а не `process.env`.
- **`store.js`** — JSON-файл через `fs/promises`; `update()` виконує зміни **по черзі** (черга промісів) і пише **атомарно** (тимчасовий файл + `rename`).
  Без черги два одночасні бронювання могли б обидва «побачити вільно».
- **`validation/*.js`** — серверна валідація: сервер не довіряє клієнту (клієнтська валідація — зручність, не безпека).
- **`routes/bookings.js`** — перевірка даних → у черзі: місце існує? → перетин `start1 < end2 && start2 < end1`? → 409 або запис; вартість рахує сервер.
- **`errors.js` + `errorHandler.js`** — `throw new HttpError(404, …)` з будь-якого місця; обробник перетворює на JSON-відповідь. В Express 5 помилки з `async`-обробників потрапляють сюди автоматично.
- **Клієнт:** `client/src/api/api.js` — `fetch` до `${VITE_API_URL}/api/...`; `ApiError` із кодами `VALIDATION`, `CONFLICT`, `NETWORK`; форми показують помилки сервера біля полів.

## Що показати викладачу
1. Два термінали: `cd server && npm run dev` і `cd client && npm run dev`; відкрити сайт.
2. `docs/API.md` і колекцію в Postman: пройти Runner (усі зелені), показати 201 / 400 / 404 / 409.
3. З інтерфейсу: `/manage` → додати місце → воно з'явилось у каталозі → видалити (підтвердження); спроба видалити місце A1 → 409.
4. Бронювання: зайнятий час → помилка; два вікна браузера з одним слотом → другий отримує 409.
5. `server/.env.example` і те, що `.env` не в репозиторії; `VITE_API_URL` у `client/.env.example`.
6. Вимкнути сервер → сайт показує зрозумілу помилку.
7. Уміти внести невелику зміну: напр., змінити години роботи (`OPEN_HOUR`/`CLOSE_HOUR` у `server/src/utils/booking.js`) або мінімальну довжину опису.
