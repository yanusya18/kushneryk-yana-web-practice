# Підготовка до захисту ПР 1

## 1. Чим функціональні вимоги відрізняються від нефункціональних?
**Функціональні** описують, *що система робить* (функції). Приклад з ТЗ: FR-5 —
бронювання місця на дату й час. **Нефункціональні** описують, *як* вона це робить
(якість): NFR-1 — адаптивність на 360/768/1280 px; NFR-2 — Lighthouse Performance ≥ 90.

## 2. Чим відрізняються git merge і git rebase?
`merge` об'єднує гілки, створюючи окремий merge-коміт, історія зберігається як була
(з розгалуженням). `rebase` «переносить» коміти гілки поверх іншої, роблячи
історію лінійною, але переписує коміти (не робіть rebase опублікованих спільних гілок).
У нашій практиці PR зливається через merge.

## 3. Навіщо потрібен .gitignore і що не можна комітити?
Файл вказує Git, які файли ігнорувати. Не комітимо: `node_modules/`, `.env` та інші
секрети (ключі API, паролі), збірку `dist/`, логи, кеш, системні файли. Шаблон змінних —
у `.env.example` (без реальних значень).

## 4. Опишіть взаємодію клієнта і сервера
Клієнт (React у браузері) надсилає HTTP-запити до Express API у форматі JSON
(`GET /api/items`, `POST /api/bookings`). Сервер перевіряє дані, перевіряє
доступність місця, зберігає у JSON-файл і повертає відповідь зі статус-кодом
(200, 201, 400, 404, 409, 500). Клієнт відображає результат користувачу.
