# Підготовка до захисту ПР 6

## Контрольні питання
**1. Що таке DOM і як браузер його будує?**
DOM (Document Object Model) — дерево об'єктів, яке браузер будує з HTML: розбирає розмітку (parsing), створює вузли-елементи й текстові вузли. JavaScript через DOM читає й змінює сторінку (`querySelector`, `textContent`, `classList`, `addEventListener`). Разом із CSSOM дерево формує render tree, за яким браузер малює сторінку. У проєкті: `catalog.js` створює картки й вставляє їх у `#workspace-list`.

**2. Поясніть спливання подій і делегування.**
Подія (напр., `click`) спочатку виникає на найглибшому елементі (`event.target`), а потім «спливає» (bubbling) вгору по предках до `document`. Делегування — один слухач на предку замість багатьох на нащадках; потрібний елемент знаходимо через `event.target.closest(...)`. Переваги: менше слухачів, працює для елементів, доданих пізніше. У проєкті: `initCardClicks(list)` у `ui.js` — клік по картці, створеній після `fetch`, відкриває сторінку місця; у `form.js` один слухач `input` на всю форму.

**3. Чим `fetch` відрізняється від `XMLHttpRequest`? Що повертає `fetch`?**
`fetch` — сучасний API на Promise (працює з `async/await`), чистіший синтаксис, потокове читання тіла відповіді. `XMLHttpRequest` — старий, на колбеках і подіях. `fetch` повертає `Promise<Response>`; він **не кидає помилку на 404/500** (лише при мережевій помилці), тому перевіряємо `response.ok`, а тіло читаємо через `response.json()` (теж Promise). Див. `api.js → fetchJson`.

**4. Чому клієнтської валідації недостатньо для безпеки?**
Код у браузері користувач контролює: може вимкнути JS, змінити HTML у DevTools або надіслати запит напряму (Postman, `curl`) — обійшовши всі перевірки. Тому клієнтська валідація — це зручність (швидкий зворотний зв'язок), а справжня перевірка й захист (від подвійного бронювання, некоректних даних, ін'єкцій) мають бути на сервері — це ПР 8.

## Ключові фрагменти коду
- **`debounce`** (`utils.js`): зберігає `timerId` у замиканні; кожен новий виклик скидає таймер, тож `render` виконається через 300 мс після останньої літери.
- **`overlaps`** (`booking.js`): `startA < endB && startB < endA` — проміжки перетинаються; рівні межі (13:00 і 13:00) — ні.
- **`initFormValidation`** (`form.js`): набір правил `{ поле: (value, values) => текстПомилки }`; показує помилки під полем (`aria-describedby`, `aria-invalid`), блокує кнопку, фокусує перше хибне поле.
- **`<dialog>`** (`ui.js`): `showModal()` дає блокування фону, фокус-пастку й закриття по Esc; клік по `::backdrop` ловимо через `event.target === dialog`.
- **Тема**: `data-theme` на `<html>` + `localStorage`; inline-скрипт у `<head>` застосовує її до малювання сторінки.
- **`new URL('../data/workspaces.json', import.meta.url)`** — шлях рахується від самого модуля, а не від сторінки.
- **`escapeHtml`**: дані вставляються через innerHTML, тому текст екранується (захист від XSS).

## Що показати викладачу
1. Запуск через Live Server (чому не `file://`: CORS і модулі).
2. Каталог: debounce (Network/Elements), стани через `?demo=...`.
3. Бронювання: валідація, зайнятий час, модальне вікно; localStorage у DevTools → Application.
4. Делегування: один слухач у `ui.js`, клік по картці.
5. Готовність внести зміну наживо: напр., змінити debounce на 500 мс або додати тип місця.

## Чесно про межі
Бронювання зберігаються в localStorage вашого браузера, тому інший користувач їх не бачить; спільна база й серверна перевірка — ПР 8.
